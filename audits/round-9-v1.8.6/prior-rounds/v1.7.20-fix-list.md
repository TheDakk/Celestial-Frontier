## High

### CF1720-01 — The Earth-Atlas restore is guarded by a condition that is false on every *completed* training run

**I initially marked this fixed and I was wrong — my first test skipped training immediately, which
is the uncommon path.** Re-tested properly:

```js
if(_tutEarthEntry && !logMap.has('p133')){ logMap.set('p133', _tutEarthEntry); … }   // 24571
```

Step 4 of training *requires* the recruit to re-chart Earth in order to advance
(`when:(t,d)=>t==='atlas-add'&&d.id==='p133'`, 24139) — `startTutorial`'s own comment at 24675 says
so. So by the time `_tutEnsureEarth()` runs at the finale or on a post-step-4 skip, `logMap.has('p133')`
is **true** (the recruit's fresh stub is sitting there), the guard fails, and the stashed entry is
never put back.

Measured, both routes:

```
skip BEFORE step 4      fav true → true    t 1785202635882 → 1785202635882    ✓ preserved
progress PAST step 4    fav true → false   t 1785202635882 → 1785202686593    ✗ rebuilt as a stub
```

The second is what a player who actually runs the training does. The ☆ favourite, the original
discovery timestamp and the Atlas ordering are all lost, which is what the release note says is fixed.

It is also dead on the reload path this round is named for: `_tutEarthEntry` is a plain in-memory
`let` (23629) and is not in the `tsnap` payload, so after a reload it is already `null`.

**Fix:** drop the `!logMap.has('p133')` condition and merge instead —

```js
if(_tutEarthEntry){
  const c=logMap.get('p133');
  logMap.set('p133', c ? Object.assign({}, c, {fav:_tutEarthEntry.fav, t:_tutEarthEntry.t,
                                               badge:_tutEarthEntry.badge, sub:_tutEarthEntry.sub})
                       : _tutEarthEntry);
  _tutEarthEntry=null; logCountEl.textContent=logMap.size;
}
```

And add it to the `tsnap` payload if the reload case is meant to be covered.

### CF1720-02 — The recovery handler snapshots the live, training-contaminated stats instead of the payload's

The new rebuild reads six of the payload's ten fields and silently substitutes live values for the
other four. Side by side with `startTutorial`'s own rebuild, which does it correctly:

```js
// startTutorial, 24654-24657 — reads the payload
stats:(p.st&&typeof p.st==='object')?{...p.st}:{...stats},
pstats:(()=>{ …clamped from p.ps… })(),
ach:Array.isArray(p.ac)?p.ac.slice(0,500):[...unlocked],
essence:Number.isFinite(+p.es)?Math.max(0,Math.min(1e9,+p.es)):essence,

// recovery handler, 25590 — reads the LIVE values
stats:{...stats}, pstats:{...pstats}, ach:[...unlocked], essence:essence,
  codexSnap:_capA(p.c,…)  cargo:_capA(p.ca,…)  cgx:_capA(p.cx,…)  items:_capA(p.it,…)   // ← these do use p
```

`doSave` writes all ten (`tsnap:{st,ps,ac,es,c,ca,cx,it,eq,ea}`, 16208). The inconsistency inside one
object literal is what marks it a slip rather than a choice.

**Consequence:** at this point in boot the live values are the *mid-training* ones. `_tutCleanup` then
"restores" `stats` to itself, so every training mutation is baked in permanently and persisted by the
`queueSave()` two lines later — the Training-Cache specimens' effect on `stats.hybrids`/`best`/`maxGen`,
the feed and breed counters, the heal step's permanent battle-stat growth (and therefore an inflated
`HP_MAX`), and any achievement unlocked during the lessons. The key-deletion sweep at 24532
(`if(!(k in _tutSnap.stats)) delete stats[k]`) is neutered too, since `_tutSnap.stats` *is* `{...stats}`.

**Fix:** mirror lines 24654-24657 exactly.

## Medium

### CF1720-03 — The `#hpheart` box now costs 25–27px of topbar height, and the previous approach didn't

v1.7.19 used a hit box with zero layout cost:

```css
#hpheart{display:inline-flex;…;padding:13px;margin:-13px;cursor:pointer}   /* v1.7.19 */
```

v1.7.20 replaced it with a real box in flow:

```css
#hpheart{width:44px;min-width:44px;height:44px;min-height:44px;padding:0;margin:0;…}   /* 2001 */
```

Measured against v1.7.19 on the same host:

```
                 topbar height        #hpheart
iPhone 14        88px  →  115px       38×43  →  44×44
desktop 1440    101px  →  126px       39×45  →  44×44
```

Nothing overlaps — `--topbar-h` is measured from JS at 2442 and 18 rules consume it, so everything
below simply shifts down. But the player loses ~26px of viewport permanently, on every device, and on
a 390×844 phone the header grows 31%.

**This one is partly my fault and worth saying plainly.** My responsive auditor flags any interactive
element whose bounding box is under 44px wide. v1.7.19's heart measured 39×45 — genuinely 5px short on
width — so the flag was correct. But the right correction was to widen the existing padding, not to
switch to a box that consumes layout:

```css
#hpheart{display:inline-flex;align-items:center;justify-content:center;
         padding:13px 15px;margin:-13px -15px;cursor:pointer}
```

That measures 44×44 with the same zero layout cost. I'd take the 26px back.

### CF1720-04 — The failure toast sends a panicking player toward the one button that erases the game

```js
:'Training could not start, and part of your expedition could not be restored. Do not reload — check ⚙ Settings for your backup.'   // 25601
```

There is no backup control in Settings. Reading the whole `#setpanel` markup (2065-2113): four tabs, a
note saying *"Clearing site data erases it, so back up favorites as ⇪ creature codes"*, and then
`↺ Reset Game` → `Erase Everything`. The only backup that exists is the internal `SAVE_KEY+'_bak'`
(16501), which has no UI and is consumed automatically only when the primary save fails to *parse*.

The advice is also already moot when it appears: lines 25597-25598 null `_tutSnapPending`, set
`tutDone=true` and call `queueSave()` **before** the toast — and `tutDone=true` makes `doSave` write
`tsnap:undefined` and makes `loadSave` ignore any surviving one. The payload is destroyed at the moment
the player is told to go find it.

**Fix:** say something true — *"Training could not start and part of your expedition could not be
restored. Your progress is saved; please report this — do not reset the game."*

### CF1720-05 — The recovery path is the only codex hydration site that drops the markup strip

```js
return g?{g, f:String(x.f||'').slice(0,48)||null, …}                                   // 25591 — recovery
return _sg?{g:_sg, f:String(e.f||'').replace(/[<>&"']/g,'').slice(0,48)||null, …}      // 24660 — startTutorial
if(_sg) _storeSpecies(_sg, String(e.f||'').replace(/[<>&"']/g,'').slice(0,48)||null…)  // 16405 — loadSave
```

`from` is a real `innerHTML` sink — `spCard` interpolates it raw twice (15016-15017) and the result
goes to `codexEl.innerHTML` (15061); `#rev-kind` does the same at 14813. Every entry restored through
the recovery path lands in `codex` with an unstripped `from`. **Fix:** add `.replace(/[<>&"']/g,'')`.

### CF1720-06 — `chWeek` still rewinds on a lag of two weeks or more

```js
chWeek=(()=>{ const _w=num(data.chw,-1), _n=Math.floor(Date.now()/6048e5); return (_w>_n+1)?_n:_w; })()   // 16421
```

Forward-jump freeze: closed ✓. Backward clock: closed for a one-week lag (`_w > _w` is false), but a
**≥2-week** lag makes the test true and lowers `chWeek` to `_n` — exactly the behaviour the comment
says was removed. When the clock later syncs, `_chRoll` sees `wk>chWeek` and deletes every `w`-prefixed
key from `chProg` and every `w` id from `chacc` (23701-23703): in-progress weeklies silently wiped.

It is worst where it runs — boot, before NTP has necessarily synced, is when `Date.now()` is least
trustworthy. **Fix:** stop repairing at load and let `_chRoll` do it after the clock settles —
`if(chWeek>wk+1) chWeek=wk; if(wk>chWeek){…}`.

### CF1720-07 — `body.training #tutbox{z-index:60}` is the blanket raise the codebase deliberately avoided

The per-step toggle at 24289 carries its own warning:

```js
/* z-scope (Nick's phone screenshots): the card outranks the boards ONLY on
   the sheet step … — a blanket raise put the dialogue over the very cards the lessons teach */
tutEl.classList.toggle('overtop', !!(s&&s.id==='sheet'));
```

`body.training #tutbox` is (1,1,1) versus `#tutbox.overtop`'s (1,1,0), so the new rule wins at every
step and that toggle is now dead. `#panel` is safe (the `--tut-bot` tracking at 24384 keeps it
geometrically clear), but `#helppop` at `z-index:51` is in `TUT_ALWAYS` and dismissible during
training, and on a phone its `bottom:calc(142px + safe-area)` overlaps `#tutbox.dodge`'s
`bottom:calc(170px + safe-area)` — so the ? popover now paints *under* the lesson card.
**Fix:** `body.training #tutspot{z-index:49}` and leave `#tutbox` at 50, or add
`body.training #helppop{z-index:61}`.

## Where this round leaves things

The two failure classes that defined rounds two through five — CSS in the wrong stylesheet, and a
helper out of scope — **did not recur**. Every added rule lands in the last stylesheet, every added
identifier resolves, and the critical is verifiably closed on the exact path it kept failing on.

What replaced them is subtler and, honestly, harder to catch by inspection: two fixes that run but
carry the wrong *values* (CF1720-01's guard, CF1720-02's four fields). Both are visible the moment you
assert the outcome rather than the mechanism — which is the same lesson, one level in:

```js
// not: does the restore run?      but: did it restore the right thing?
assert(logMap.get('p133').fav === preRestartFav, 'earth favourite survived');
assert(stats.hybrids === preTrainingHybrids,     'training did not inflate stats');
assert(topbar.offsetHeight <= prevTopbarHeight,  'touch fix cost no layout');
```

That last one is the general form of CF1720-03: when a fix changes a size, assert that nothing *else*
changed size.
