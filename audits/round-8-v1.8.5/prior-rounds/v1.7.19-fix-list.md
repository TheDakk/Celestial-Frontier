## Critical

### CF1719-01 — `_capA` was hoisted correctly; `_sanitizeSavedGenome` was not. Same path, same outcome.

The hoist landed, and the comment shows you already hit this once:

```js
const _capA=(a,n)=>Array.isArray(a)?a.slice(0,n):[];   // 2409 — before the first IIFE at 2452 ✓
/* CF1718-01: startTutorial needs this at TOP level — the first hoist landed inside the
   SaveSystem module and the reload path still threw (caught by the new smoke journey) */
```

But the very next helper on the same line is still inside `const SaveSystem=(()=>{ … })();`
(16093–16591):

```js
codexSnap:_capA(p.c,1500).map(e=>{ const _sg=e&&e.g&&_sanitizeSavedGenome(e.g);   // 24635
```

`_sanitizeSavedGenome` is declared at 16214, inside that module, and is not exported — the module's
destructure at 16592 exposes only `queueSave, wipeSaveAndReload, loadSave, loadSaveWithRecovery,
SAVE_KEY, readLegacySave, legacyFarewell`. (`_sanitizeView` at 16615 **is** outside the module and
is fine — only one of the two is unreachable.)

**Your new logging is what proved it.** Driving the real journey — veteran save → ⚙ Restart →
advance a step → reload:

```
console: training start failed
         ReferenceError: _sanitizeSavedGenome is not defined
             at game.html:24635:57
             at Array.map (<anonymous>)
             at startTutorial
```

**And the recovery handler cannot compensate, for a subtle reason.** The handler is well designed:

```js
setTimeout(()=>{ try{ startTutorial(); }catch(e){
  try{ console.error('training start failed', e);
    if(_tutSnap||_tutSnapPending){ _tutSnap=_tutSnap||null; _tutCleanup(); }
    tutDone=true; _syncRecruit(); queueSave();
    toast('🛟 Training Recovery','Something interrupted training — your expedition was restored safely.');
  }catch(_){ } } }, 800);                                                                  // 25556–25560
```

But `_tutSnapPending` is nulled one line *before* the throw (24629), and the throw happens *inside*
the `_tutSnap={…}` assignment — so `_tutSnap` is never assigned either. `if(null||null)` is false,
`_tutCleanup()` never runs, and the handler proceeds to `tutDone=true; queueSave()`.

Measured end state, and the toast is the part that stings:

```
save after reload      codex 0   cargo 3   items 3   eq 3   tut 1   tsnap gone
on screen              🛟 TRAINING RECOVERY — "your expedition was restored safely."
Compendium counter     0
```

Cargo, items and gear survive (those are only cleared by `_tutCleanup`, which never ran). The
Compendium does not — it was emptied at training start and its only copy was the `tsnap` payload the
failed restore threw away.

**Fix, two parts:**
1. Move `_sanitizeSavedGenome` out of the SaveSystem IIFE to sit beside `_capA` at 2409 — or export
   it in the module's return object and destructure it at 16592.
2. Make the recovery handler survivable: do not null `_tutSnapPending` until the assignment
   succeeds. `const p=_tutSnapPending; _tutSnap={…}; _tutSnapPending=null;` — then the catch has
   something to restore from no matter where inside the object literal it fails.

Part 2 matters more than part 1. It is what turns the *next* scope slip into a recoverable event
instead of a data-loss event.

## Fixes with a placement or logic defect

### CF1719-02 — The Earth-Atlas-entry restore was patched into the wrong function and never executes

The stash is right, at `startTutorial` (24653):

```js
try{ _tutEarthEntry=logMap.get('p133')||null;   /* CF1718-07: the delete cost the ☆ flag, timestamp and badge */
  logMap.delete('p133'); …
```

The restore landed in `startNewGame()` (15434) instead of `_tutEnsureEarth()`. The indentation gives
it away — the inserted line sits at 8 spaces, and the line right after it, which belongs to the
*original* block, sits at 4:

```js
      if(tutDone){
        const where={…};
        if(!logMap.has('p133') && _tutEarthEntry){ logMap.set('p133', _tutEarthEntry); _tutEarthEntry=null; }
    if(!logMap.has('p133')){                                   // ← 4 spaces: this is _tutEnsureEarth's indentation
          logMap.set('p133', {id:'p133', title:'Earth', … t:Date.now()});
```

Four spaces is exactly the indentation of the identical line at 24553 inside `_tutEnsureEarth` — the
function that actually rebuilds Earth on every training exit, and which is **untouched**.

It is also unreachable where it sits: the enclosing `if(tutDone)` is false at both `startNewGame()`
call sites (after `resetMemoryState()` sets `tutDone=false`, and on a fresh boot where `loadSave`
returned before assigning it).

**Consequence, measured.** Driving the real journey — skip training, then ⚙ Restart, then skip again:

```
Earth Atlas entry t   before restart  1785191618287
                      after  restart  1785191635960   ← rebuilt with Date.now()
```

The entry is reconstructed, not restored. The stub literal at 24553 carries no `fav` key, so the ☆
favourite flag goes with it — and `fav` is a real persisted field (restored by the loader at 16446),
drives the ☆ filter at 14279 and the `favCount` badge at 14289, and unlocks the `curator` achievement
at 14107. Atlas ordering resets too, since rows sort on `t`. Exactly what the changelog says is fixed.

*(I confirmed the timestamp directly. I could not cleanly demonstrate the ☆ loss end-to-end — my
attempt to seed the flag was overwritten by the game's own 900 ms autosave debounce before the
reload — so that half rests on the code path rather than a measurement.)*

**Fix:** delete line 15434; put the restore immediately before line 24553 in `_tutEnsureEarth()`.
And null `_tutEarthEntry` on the other exit paths (`tutAbort`, `resetMemoryState`) — it is currently
never cleared, so a stale stash from one expedition can leak into the next.

### CF1719-03 — The `chWeek` clamp closes the forward-jump freeze but reopens the backward-clock re-roll

```js
chWeek=Math.min(num(data.chw,-1), Math.floor(Date.now()/6048e5))   // 16410
```

against the rollover test, which is correct:

```js
function _chRoll(){ const wk=_chNow();
  if(wk>chWeek){ chWeek=wk; /* wipe every w-prefixed chProg key and w id from chacc */ }   // 23679
```

`Math.min` *lowers* a legitimately banked `chWeek` whenever the device clock is behind the save. So:
set the clock back a week → reload (`chWeek` 2900 → 2899) → set the clock forward again → `_chRoll`
sees `2900 > 2899`, wipes the weekly slate, and `_chWeekly()` re-seeds from the same `chWeek` — the
same three charters, progress reset, claimable again. Repeatable.

The benign version is worse in practice: any device whose clock is briefly wrong at boot (a VM, a
dead CMOS battery, NTP not yet synced) silently wipes the player's in-progress weekly charter counts
the moment the clock corrects.

**Fix:** only treat *impossibly far future* values as corrupt, and never lower a banked week —
`const _w=num(data.chw,-1), _n=Math.floor(Date.now()/6048e5); chWeek = (_w > _n+1) ? _n : _w;`

### CF1719-04 — The focus-restore guard includes `#panel`, so it skips the most common case

```js
try{ if(typeof PANELS==='undefined' || !PANELS.some(p=>{ try{ return p.open(); }catch(_){ return false; } })) _restoreFocus(); }catch(_){ }   // 5605
```

The intent — don't steal a return target that still belongs to an open board — is right. But
`PANELS` ends with the survey card:

```js
{id:'panel', el:()=>panelEl, btn:null, x:1,                                  // 25144
 open:()=>!!(panelEl && panelEl.style.display && panelEl.style.display!=='none'), …}
```

`btn:null`, so `#panel` can never *be* a focus-return target (the manager at 25087 only assigns
`_focusReturn` from `p.btn`). Including it in the guard blocks the restore for a panel that has
nothing to protect — and the survey card is open in the most common flow there is.

**Failure:** tap a planet → survey card opens → tap Share → `#sharebox` takes focus → Escape. The
card is still open, so the guard skips `_restoreFocus()`, and focus falls to `<body>`. Same for
`#descbox`, `#vistabox`, `#reveal`, `#itemcard` and `#platebox` opened over a card. That is
CF1715-13 reintroduced for the majority case.

**Fix:** `!PANELS.some(p => { try { return p.btn && p.open(); } catch(_) { return false; } })`

## Smaller items from this round's changes

- **CF1719-05 — `role="img"` on a focusable canvas defeats the label it carries.** (2348) `role="img"`
  declares a static graphic, so NVDA and JAWS keep browse mode active on focus and consume the arrow
  keys, Enter and ± before the handler at 5516 sees them. The `aria-label` promises four bindings and
  none of them reach the game. `role="application"` was the heavy-handed choice and this is the
  over-correction; the workable middle is `role="application"` on the canvas alone (it suppresses
  browse mode for exactly one node, which is the correct trade for a keyboard-driven canvas), or a
  `role="group"` with `aria-describedby` pointing at a visually-hidden key list.
- **CF1719-06 — `#namein` still loses the tablet 16px floor.** (1957) `#namein{font-size:16px}` is one
  ID; `#namebox #namein{…font:600 14px…}` at 440 is two, and wins regardless of order. The `!important`
  went on `#searchin` and the sibling was left. On iPad and Surface the "name your explorer" field is
  still 14px, so Safari auto-zooms on focus — the exact defect the rule exists to prevent.
  **Fix:** `#namebox #namein,#searchin{font-size:16px}` and drop the `!important`.
- **CF1719-07 — `.bslot.miss{opacity:1}` inverts the hover cue.** (1988) `.bslot.pslot.miss:hover`
  (1592) is more specific and still sets `opacity:0.9`, so empty paragon slots — which are clickable,
  `role="button" tabindex="0"` at 15232 — now **dim** on hover instead of brightening. Change 1592 to
  `opacity:1` and let the border colour carry the hover.
- **CF1719-08 — `body.training #tutspot{z-index:59}` outranks the training card.** (1986) `#tutbox` is
  50, and `#tutspot.overtop` (59) only applies on the `sheet` step. On the other 20 steps the ring now
  draws *across* the guidance card during its 250 ms position transition, and above `#helppop` (51) and
  `#deathbox` (50), both reachable in training. Bounded — the ring is `pointer-events:none` — but
  pair it with `body.training #tutbox{z-index:60}`.
- **CF1719-09 — `#reveal .rgrp.open .rghead .v{opacity:1}`** (1989) fixes the contrast and removes the
  expand/collapse state signal at the same time; the collapsed summary and the expanded body now read
  at equal weight. Not a defect, but the affordance is gone — consider a weight or size difference
  instead of opacity.

## The pattern, one last time

Four rounds, four fixes shipped into a place they could not run: a CSS block in the wrong
stylesheet (twice), a helper outside its scope (twice), and now a restore in the wrong function.
Every one of them was correct code.

The good news is that the two mitigations you added this round — logging the boot catch, and a smoke
journey that walks the reload path — are exactly the right ones, and the logging is what made this
round's bug a one-run diagnosis. The gap is that the smoke journey passes while the bug is live,
which means it asserts that training *starts*, not that the Compendium *came back*. Three assertions
would close this class for good:

```js
// after the reload-path smoke journey
assert(codex.size === preRestartCodexSize, 'compendium restored');
assert(logMap.get('p133').t === preRestartEarthT, 'earth atlas entry preserved');
// after any CSS change to a control size
assert(getComputedStyle(bell).width === '44px', 'touch target applied');
```

Assert the *outcome the fix promises*, not that the code path ran.
