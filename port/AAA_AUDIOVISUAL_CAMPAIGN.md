## 1. The game and the ambition

Celestial Frontier is a browser-native, offline-capable, deterministic exploration and collection game, designed first for iPhone. Its universe contains galaxies, star systems, planets, 43 biome profiles, 1,010 canonical Earth species, procedural aliens, a 47-material economy, equipment, evolving ship presentation, companions, Guardians, and combat. The 1,014 compatibility routes are not 1,014 distinct species.

The core loop is:

**Discover → Learn → Gather → Build → Raise → Risk → Return → Reach farther**

The inspiration combines an infinite sandbox and creature-collection chase, earned equipment depth, memorable hunts, and a constructive exploration/building progression. These comparisons guide quality and player experience; they do not authorize importing another game's mechanics or inventing missing loot tables.

The identity is alien, painterly, mature, and readable: a MUD/EverQuest-inspired voice in which color and words carry meaning. Build on the existing universe, portraits, genetics, persistence, workers, renderer, and procedural audio. The premium-quality target is coherence, atmosphere, responsiveness, craft, and attachment within a browser and phone budget.

Nothing is monetized through paid randomness, nothing expires to pressure attendance, and leaving the game carries no punishment. No FOMO, streak decay, offline-income requirement, hidden odds, or compulsory maintenance.

CSS and semantic HTML retain accessible chrome, text, controls, and layout. This exception does not grant a blanket portrait repaint or silently remove other art rules.
- Icon masters are at least 144px. Preserve bespoke material identity; do not replace 47 material masters with family recolors. Match light direction, depth, detail density, and small-size readability.

### Interface, accessibility, and copy

- Use one palette, type hierarchy, spacing system, radius/depth treatment, icon language, motion grammar, and sound grammar. Prefer one clear primary action, with secondary actions quieter but reachable.

## 14. Blender production workflow

### 14.1 Establish one asset pipeline

1. Record the installed Blender version and inspect hardware/render capability without assuming GPU availability. Create one pilot scene with one camera, named collections, a consistent scale/origin, color management, lights, and transparent-background output where needed.
2. Create art-directed assets in Blender. Use shapes, materials and light to match the painterly game; photorealism is not the default target. Prefer readability at actual game size over detail visible only in a render window.
3. Save `.blend` sources and all required textures alongside reproducible scripts/export settings. Eliminate developer-specific absolute paths. Include a source/renderer version and recipe so an export can be regenerated.
4. Render/bake expensive detail offline. Cycles versus EEVEE is a measured per-asset choice; neither becomes a device requirement. Do not promise identical pixels across Blender versions or render hardware.
5. Derive runtime variants, then inspect them after integration. Check transparent edges, color conversion, filtering, compression, atlas padding, pivots and cropping; an excellent master can still look wrong after downsampling or compositing.
6. Load through existing bounded owners. Retain disposal, lazy loading, cancellation, context recovery and a usable fallback. No base64 duplication or unbounded texture registry as an integration shortcut.

Blender provides both Cycles and EEVEE rendering workflows. Their role here is authoring and offline production, not replacing the browser game engine. [Blender rendering](https://www.blender.org/features/rendering/)

### 14.2 Choose representation by asset

| Asset | Preferred pilot representation | Reason and required comparison |
| --- | --- | --- |
| Ship hull/hardpoints | Rendered views or layered parts from a Blender master | Consistent construction and lighting; compare view count versus texture cost |
| Materials/gear | High-quality still masters with size variants | Rich material identity at low runtime cost; preserve bespoke silhouettes |
| Vista elements | Layered renders/textures composited with existing generated scene | Depth and atmosphere without storing a movie for every biome |
| Planet detail | Reusable baked maps/layers combined with the current planet presentation | Retain procedural breadth and avoid one giant asset per generated planet |
| Living creature | Small comparison of bounded frame animation and compatible 2D mesh/skeletal presentation | Select by anatomy, fidelity, integration cost and measured phone memory |
| Effects | Reusable masks/textures with controlled runtime compositing | Avoid expensive full-frame animation or excessive transparent overdraw |

Do not install or commit to a new skeletal runtime merely because the master plan names one. Evaluate compatibility, licensing, authoring effort and phone cost in the pilot. A Blender rig does not automatically become a Pixi-compatible live rig; prerendering and runtime deformation are different delivery paths.

Full real-time 3D models, a second renderer, and an Unreal/native edition remain separate architectural proposals if a concrete limitation later justifies them. They are not necessary for the initial visual upgrade.

### 14.3 Protect procedural variety and animation truth

Use canonical phenotype to select compatible body/animation families, proportions, sockets and presentation materials. Do not regenerate genomes from model parameters or replace infinite procedural variation with a finite handful of generic models.

Hybrid animation must respect compatible joints, attachments and silhouette. If a specimen cannot be represented faithfully, preserve its correct static portrait and mark living coverage incomplete; do not distort it or claim the fallback closes Gate E. Generalized rigs require representative extremes and long-tail inspection before production scale.

Combat and interaction animation consumes the existing settled transcript/event. It must not move hit timing, grant damage, create outcomes, or make nonlethal actions look fatal. Keep presentation-only expression separate from immutable creature identity. Do not apply enemy battlefield scaling to owned companions.

### 14.4 Phone asset budgets

Measure decoded texture memory, atlas page count, upload spikes, simultaneous visible animations, transparent overdraw, draw calls where available, and cold/warm loading. Compressed file size is not GPU memory size. Long frame sequences can overwhelm a phone even when downloads look small.

Choose resolution, frame count, atlas dimensions and active-animation limits from pilot measurements and existing budgets; do not invent universal numerical targets before measuring. High-resolution source masters remain available while device-specific exports are bounded. Static mode must look intentionally finished, not like an animation paused awkwardly.

## 15. REAPER and Surge XT audio workflow

### 15.1 Verify the production setup

Launch REAPER, scan the chosen Surge XT plugin format, load one instrument and one effects instance, save/reopen a tiny test project, then render a short cue and replay it in the browser. Record REAPER/Surge versions, patch state, render settings and dependencies. Verify scripting/export access rather than assuming installation proves control.

Use a reusable REAPER template with organized music, ambience, creature, ship/gameplay, combat and UI groups corresponding to the game's existing bus intentions. Keep tracks named, sources relative, automation explicit and output routing clear. Do not add a second runtime mixer owner.

### 15.2 Create the source material

- **Music:** author motifs, harmony and arrangement in REAPER. Surge supplies playable synthesis for pads, basses, pulses and textures. Render separately controllable layers only when the game can mix them meaningfully; preserve aligned start, length and loop boundaries. Do not confuse a held synth preset with a finished soundtrack.
- **Ambience:** compose environmental beds and sparse details. Avoid obvious short repetition, clicks and relentless motion. Vacuum, caves and abyss may use different kinds of quiet; silence should support each environment rather than imply identical acoustics everywhere.
- **Creature voices:** start from existing family/register/phrase identity. Add compatible authored textures or processed layers without substituting a random preset for each species. Validate that the same creature remains recognizable across its allowed expressions.
- **Ships and equipment:** layer transient, body and tail components for engines, landing, fabrication, mining and equipment operations. Different capabilities should sound distinct without creating louder-is-better progression.
- **Combat and milestones:** create restrained cues that clarify transcript events and make Guardian/Prime moments distinctive. Test dense event sequences so a pleasant isolated cue does not become exhausting in play.
- **UI:** build a compact related family of navigation, activation, refusal and settlement sounds. Prioritize meaningful feedback and avoid a sonic barrage during rapid navigation.

Surge XT can produce commercially usable sounds, including from its factory presets. Third-party samples, wavetables, impulse responses and patches may carry separate terms and still need review. [Surge XT usage FAQ](https://surge-synthesizer.github.io/faq/)

### 15.3 Preserve determinism correctly

REAPER and Surge operate offline during asset production. They do not generate gameplay randomness at runtime. Some synth patches use free-running oscillators or modulation; final approved rendered files are the distribution authority, with retained checksums, even if a later rerender is not sample-identical.

Runtime variation uses the existing approved presentation identity/event mapping. Never add an unversioned RNG path to pick species calls or disclose hidden roster content. If a proposed texture changes a creature's stable voice profile instead of enriching its rendering, identify that as a versioned audio-identity decision before rollout.

Current `D-CFB-1` parent-audio representation remains unresolved unless a later authoritative decision says otherwise. Do not claim a true two-parent voice blend from seed tuples alone; retain the approved deterministic fallback.

### 15.4 Edit, mix, render and integrate

1. Keep editable projects plus lossless masters. Use a documented proposed working format such as 48 kHz/24-bit WAV, subject to the verified project pipeline; browser playback may resample to the device rate.
2. Inspect clipping, tails, loop continuity, phase/mono behavior and relative levels. Establish mix references from listening and existing limits rather than normalizing every cue to the same loudness.
3. Render playback copies with formats tested in target Safari/PWA and other supported browsers. Do not assume one codec covers every target; avoid shipping duplicate encodings without a demonstrated compatibility need.
4. Publish content through the existing rights and asset owners. Retain cue identity, source, file hash, duration, loop points and applicable captions using existing manifest contracts where possible. Any necessary content-model extension is a named implementation task, not an incidental new evidence framework.
5. Integrate with the real committed action or transcript. Press/pending feedback is immediate; success sounds wait for durable success. Refusals, read-only convergence and reload do not replay rewards.
6. Measure both compressed bytes and decoded audio memory. Stream suitable long-form content where the supported lifecycle permits; buffer short responsive cues deliberately. Do not decode the entire score and all species sounds at boot.
7. Verify mute, individual buses, mono, reduced intensity, hide/resume, lost audio context, interrupted playback and rapid repeated input. Restart ambience safely after visibility returns when enabled and permitted by browser gesture policy; do not replay old one-shot events.

Source tools never ship to players. Web Audio consumes optimized local game assets, and the existing procedural synthesis remains available where it provides identity, variation or the approved fallback.

### 15.5 What audio improvement means in review

Deliver A/B comparisons at matched listening level: current game, proposed mix, music alone, ambience alone and complete scene. Include headphones and phone-speaker checks, a quiet exploration interval, a busy combat interval, and mono/reduced-intensity versions.

Nick's listening review is required. Automated waveform or loudness inspection does not prove musical appeal, biological plausibility, comfort or emotional impact. Do not label audio human-reviewed when only its files or meters have been inspected.
